1
배경 & What / Why
왜 지금, 보안 인지 캠페인인가
배경Phase 1이 확산되며 함께 온 리스크

2026년 7월 1일 Phase 1이 시작되며 다수 크루가 Claude Pro/Max 계정을 지급받았고, 이외 AI 툴 구매도 함께 늘고 있습니다. AX가 조직 전반에 자리잡아가는 지금이, 도구 확산과 함께 따라와야 할 '보안' 인식을 세우기 좋은 시점입니다. Phase 2 진입 전 Phase 1.5로 보안 캠페인을 제안합니다.

What목적

부스터스 모든 크루가 '보안'에 대한 인지를 형성하도록, Phase 1.5 단계 강의 및 캠페인을 진행한다.

Why필요성
자산 보호
AI를 활용한 여러 파일들이 아무렇게나 던져지고 있는 상황에서, 우리 자산을 보호하기 위한 인식 전환 캠페인이 필요합니다. AX 챌린지 웹사이트도 부스터스 계정 로그인으로 접근은 통제되어 있으나, 접속 이후엔 모든 크루의 결과물이 열람 가능해 개인의 도덕적 판단에만 맡기기 어렵습니다.
단계별 접근
AI 활용도와 보안 인지 정도는 크루마다 편차가 큽니다. 하나의 방식으로 전사를 동일하게 다루기보다, AI 활용도와 인지 정도에 따라 오디언스 군을 나누어 진행합니다.

AX 숙련도 × 활용 규모 기준으로 오디언스를 둘로 나눕니다

Group 1 · Target

  • 컨텐츠(What) — 무엇을 입력해도 되고 안 되는지, 흔한 실수 시나리오, 오늘부터 지킬 습관
  • 방식(How) — 전 구성원 대상 필수 교육 세션 + 교육자료 배포

  • 목표(지향점) — 자유로운 활용은 권장하되, 스스로 '선을 지키는' 기준을 함께 만든다.
  • 컨텐츠(What) — 서로 어떻게 쓰고 있는지, 쓰면서 느낀 보안 문제 의식, 앞으로의 방향
  • 방식(How) — 소규모 FGI(Focus Group Interview) 진행
2-2세그먼트를 나누는 이유
1
AX 숙련도에 따라 필요한 개입의 형태가 다릅니다 — 초급은 '기준을 알려주는 교육', 중상급은 '기준을 함께 만드는 대화'가 필요합니다.
2
실제 사용률과 영향력(민감도)의 크기(Size)가 그룹마다 다릅니다 — 이미 많이 쓰는 그룹일수록 노출되는 리스크의 총량이 큽니다.
3
두 트랙 모두 결국 하나의 문화로 '연동'되어야 합니다 — 초급 교육에서 나온 질문이 FGI 의제가 되고, FGI에서 나온 기준이 다음 교육자료에 반영되는 순환 구조를 지향합니다.

자연스러운 자산 통제 방법
교육·문화만으로 채워지지 않는 부분은 기술적 장치로 보완합니다
5-1사이트 론칭을 boosters-ax.vercel.app 파생 경로로만 한정하기

"사이트를 론칭하고 싶은 직원이 생겼을 때, 이 링크에서 파생된 경로로만 만들 수 있게 한정할 수 없는지"에 대한 실행 옵션입니다. 강도 순으로 정리했습니다.

Option A · 모노레포 통합 배포통제력 최상
모든 사이드 프로젝트를 하나의 Next.js 프로젝트 안에 /apps/[slug] 라우트로 편입합니다. 배포 자체가 하나의 도메인(boosters-ax.vercel.app)에서만 이뤄지므로, 구조적으로 도메인 밖에 사이트가 존재할 수 없습니다. 편입은 PR 리뷰를 거칩니다.
Option B · 회사 Vercel 조직 계정 통합통제력 중
개인 Vercel 계정 대신 회사 Vercel Org로 프로젝트를 이전하고, <slug>.boosters-ax.vercel.app 형태의 서브도메인만 발급합니다. 배포 권한은 Tech팀이 관리합니다.
Option C · 정책적 게이트통제력 낮음 · 시작하기 쉬움
개인 벤더(Netlify, Lovable 등) 배포 시 Tech 사전 승인을 필수로 하고, 승인된 결과물만 boosters-ax 하위로 이관받습니다. 기술 구축 없이 바로 시행 가능합니다.
✓ Phase 1.5 즉시 적용 권장
💡 제안 — 지금은 Option C(정책)로 즉시 시작하고, Option B(조직 계정 통합)를 병행 준비합니다. Option A는 사이드 프로젝트 수가 늘어나는 Phase 2 이후 고도화 과제로 Tech팀과 별도 논의합니다.
5-2AI 결과물을 boosters.kr 계정으로만 접근 통제하기

boosters-ax.vercel.app는 이미 부스터스 Google Workspace 계정으로만 로그인 가능하도록 도메인이 제한되어 있습니다(OAuth 로그인 시 boosters.kr 도메인 검증). 이 방식을 다른 AI 결과물에도 어떻게 확장할지 정리했습니다.

방식 1 · 앱마다 로그인 로직 구현개발 부담 있음
새 앱을 만들 때마다 Google OAuth + boosters.kr 도메인 검증 코드를 각각 심습니다. 지금 boosters-ax.vercel.app에 쓰인 방식과 동일하지만, 앱 수가 늘어날수록 반복 구현 부담이 커집니다.
방식 2 · 공통 접근 게이트웨이 (Cloudflare Access 등)확장성 높음
앱 코드를 건드리지 않고, 도메인/URL 앞단에 Google Workspace 연동 접근 정책(예: Cloudflare Zero Trust Access)을 씌웁니다. boosters.kr 계정이 아니면 앱에 도달하기 전에 차단되므로, 이후 만들어지는 모든 사이드 프로젝트에 로그인 로직 없이 동일한 통제를 일괄 적용할 수 있습니다.
✓ 장기 표준으로 권장 · Tech팀 기술 검토 필요
💡 제안 — Section 5-1의 Option B(조직 계정 통합)와 묶어서, boosters-ax 하위 모든 서브도메인에 공통 게이트웨이를 씌우는 방향을 Tech팀 협의 안건으로 올립니다. 크리덴셜 클린업 캠페인(CHRO 제안서, 2026.07.10)의 접근 통제 문제의식과도 같은 맥락입니다.
